## مسیر کامل تا لحظهٔ ورود حساب

- کلاینت ویندوز رابط مدیریت موتور WinGet دارد؛ حساب لازم نیست.
- پنجرهٔ «حساب‌ها و اتصال‌ها» توکن ناشر را در DPAPI همان کاربر ذخیره می‌کند؛ آزمایش TLS با گواهی و اثرانگشت مستقل انجام می‌شود.
- ZIP سرویس خصوصی، `deployment/HamApp-Service-Setup.cmd` و Docker Compose را در خود دارد. پس از نصب Docker Desktop، عامل روی رایانهٔ مالک با اجرای یک CMD فقط سرویس خودش را می‌سازد؛ سرویس‌ها/شبکه‌ها/ولوم‌های دیگر را حذف نمی‌کند.
- اولین راه‌اندازی محلی می‌تواند **گواهی TLS صرفاً برای localhost** بسازد؛ این گواهی برای دامنهٔ عمومی قابل‌استفاده نیست و هرگز جای کلید امضای واقعی برنامه نیست.
- ثبت ناشر، ساخت صف خصوصی، نمایش یک‌بارهٔ توکن، چرخش/ابطال توکن، ثبت CA عمومی و ذخیرهٔ DPAPI همگی به همین بک‌اند متصل‌اند.
- اندروید بدون کلاینت جانبی F-Droid از فهرست رسمی استفاده می‌کند؛ مخزن شخصی فقط با نشانی و اثرانگشت معتبر وارد می‌شود؛ کلید خصوصی امضا هرگز وارد اپلیکیشن عمومی نمی‌شود.

## چیزهایی که صادقانه کامل نیستند

این ادغام به معنای «هر قابلیت تمام موتورهای OSS انتخاب‌شده در محصول با همان UX کامل» نیست. موتور WinGet از طریق سطح فرمان خود قابل‌استفاده است ولی بعضی گزینه‌های خطربار محدود شده‌اند؛ تنها کتابخانهٔ ایندکس F-Droid در کلاینت اندروید استفاده می‌شود، نه همهٔ کتابخانه‌های پایگاه داده/دانلود و مدیریت تمام چرخهٔ رسمی F-Droid. بنابراین **فهرست نواقص محصول نباید به صفر تبدیل شود**.

بازارگاه عمومی چندناشر با احراز هویت پیشرفته، مدیریت نقش‌ها، تأیید قانونی ناشران، پنل مستقل، تأیید و ارتقای نسخهٔ تولیدی، مدیریت پرداخت‌ها و تنظیم امضای پایدار هنوز به اطلاعات معتبر، طراحی/پیاده‌سازی و زیرساخت بیشتری نیاز دارد. افزودن ناخواستهٔ Payload، WinGet REST، UniGetUI یا Droid-ify به‌عنوان موتور موازی مشکل را حل نمی‌کند.

## امنیت و بهره‌برداری

- کلید خصوصی امضای اندروید/ویندوز یا F-Droid، رمز تولیدی و اطلاعات کاربری در کد یا Artifact عمومی قرار نمی‌گیرد.
- همهٔ ساخت‌های Pull Request روی رانرهای میزبانی‌شدهٔ GitHub اجرا می‌شوند؛ اجرای کد بازبینی‌نشده روی رانر خودمیزبان ممنوع است.
- در CLI پیشرفتهٔ WinGet هیچ shell، اجرای فرمان عمومی، دانلود با عبور از هش، پذیرش بی‌صدای مجوزها یا نصب ناشناس بدون تأیید کاربر وجود ندارد.
- سرویس Docker فقط `127.0.0.1` میزبان را باز می‌کند، سطح اجرای ریشه ندارد، filesystem برنامه read-only است و داده‌ها در volume خصوصی نگه داشته می‌شوند.
- تا وقتی نصب واقعی روی دستگاه و تولید کلیدهای معتبر انجام نشده‌اند، وضعیت فنی فقط «آمادهٔ پیکربندی/آزمون» است، نه PASS عملیاتی عمومی.

## شواهد لازم برای قبول PR

`python -m unittest discover -s tests -v`، build واقعی Docker Compose، TLS socket+توکن واقعی موقت و قرنطینه، بازتولید ZIP سرویس، CI لینوکس و ویندوز، ساخت Android APK، Windows EXE/NSIS، اجرای رابط روی شبیه‌ساز، بررسی مجوزهای APK، CodeQL و امضای artifactهای آزمایشی. هر نتیجه باید به دقیق‌ترین SHA اشاره کند و ساخت روی main بعد از ادغام تکرار شود.
