# Native binary provenance from trusted GitHub workflows

The Android debug APK and unsigned Windows EXE now use **GitHub first-party signed build attestations**.

On trusted main only, a separate job downloads the exact artifact generated by the existing build job, uses actions/attest@v4 to attest those bytes, and independently checks them with gh attestation verify. Verification pins:
- Repository: rezamahrm100-ops/hamapp-store
- Workflow: the corresponding android-client-preview.yml or windows-client-preview.yml
- Ref: refs/heads/main
- Source digest: the complete GITHUB_SHA
- Runner policy: --deny-self-hosted-runners

Untrusted pull-request code cannot invoke the attestation job. The build jobs have read-only permissions. The attestation jobs have explicit minimum OIDC/attestations permissions and run on GitHub-hosted Linux, not the owner Windows machine.

The JSON review receipt is generated only after gh CLI verification succeeds. The Python script itself **does not perform cryptographic verification** and a forged JSON file must never be accepted as independent proof. The receipt records sha256, artifact name, source SHA and explicitly false claims for production signing, F-Droid index, owner approval and device installation.

No release is published, no key is created and no catalogue download is activated. The Android APK is debug signed; the Windows EXE is unsigned. The GitHub attestation is NOT developer APK signing, Windows Authenticode, F-Droid repo signing or device QA.

For a real publisher release: verify its own producing repository's signed provenance and repository ID, a separately owner-approved signer certificate, verified exact binary bytes, anti-rollback and isolated test-device install/update. The current signer and history records stay empty.

Reference: https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations
