# HamApp — real Windows-hosted Authenticode EXE signing and rejection acceptance

## Engineering objective
The Windows preview previously produced a real **unsigned** PyInstaller EXE and only mocked signature/publisher verification on candidate packages. The hosted `windows-client-preview.yml` pipeline now produces the same real EXE, keeps it **UNSIGNED** as the short-lived preview artifact, and signs **two separate temporary copies** using different Windows CodeSigningCert certificates generated on **ephemeral GitHub-hosted Windows**. This is authentic Windows cryptographic signing, not a mocked PowerShell success flag.

The drill:
1. Generates two independent RSA-2048 test identities with pinned upstream `pyca/cryptography==50.0.2` (OpenSSL) and explicit code-signing EKU (`1.3.6.1.5.5.7.3.3`), serializes each as a password-protected disposable PFX only under `RUNNER_TEMP`. Both native Windows CNG routes — `New-SelfSignedCertificate` and `.NET CertificateRequest.CreateSelfSigned` — genuinely blocked on GitHub-hosted Windows, as shown by separate eight-minute timed-out runs; the third implementation does not call those Windows key providers to create private keys. Temporary trust is limited to `Cert:\CurrentUser\Root` and `Cert:\CurrentUser\TrustedPublisher` on the isolated hosted runner.
2. Signs two actual preview EXE copies with official Windows SDK `signtool.exe sign /f <temporary-PFX> /fd SHA256`, verifies using `signtool.exe verify /pa`, rechecks native `Get-AuthenticodeSignature` through the existing `scripts/publisher_gate.py`, and computes SHA-256 fingerprints of actual signer DER certificates. Only the PUBLIC certificates enter the temporary CurrentUser trust stores; no PFX private key is imported into a Windows CNG container.
3. Constructs a **synthetic local-only, not-published** candidate and source registry and verifies the intended signer and precise EXE digest; rejects the unsigned original, the other *genuinely signed* EXE under the first publisher pin, and an EXE altered after signing.
4. Emits a bounded JSON receipt whose `public_release_authorized`, `production_authenticode_certificate_verified`, `trusted_prod_publisher_registered` and `windows_real_install_or_upgrade_verified` are explicitly **false**. Removes temporary public trust certificates from CurrentUser stores, deletes the password-protected disposable PFX files, signed test EXEs and all temporary workspace bytes. Only an unsigned preview artifact and **receipt without keys or executable** are eligible for upload.

## Exact scope and trust limitations
- A **temporary self-signed certificate deliberately imported into the runner's CurrentUser trust store is NOT a real publisher/production Authenticode certificate**, public PKI identity, SmartScreen approval, hardware-backed signer or publisher registration.
- No private owner product, user secrets or persistent certificate is handled by public PR builds. The trusted owner Windows runner remains main-only and is not used for this drill.
- Windows GUI preview remains unsigned and not installable as production. No unreviewed WinGet package is mapped and real installer elevation/UAC/update/rollback never runs on the owner's machine.
- Source unit tests never substitute for Windows PowerShell and real signed EXE results; require successful actual hosted Windows run and saved evidence under `hamapp-real-ephemeral-windows-authenticode-evidence`.

## Remaining real-world gates
Owner-approved developer certificate SHA256, hardware/secure signing key custody, independently verified source/release provenance, signed approved Windows installer, exact WinGet package mapping, consented Windows package install/update/rollback, user rights and public deployment remain blocked. No synthetic fixture or temporary key can approve any of these.

### Independent tooling revision and real acceptance boundary
Initial hosted test on PR #56 stalled specifically during `New-SelfSignedCertificate` and terminated at the eight-minute per-step timeout; next hosted attempt with .NET `CertificateRequest.CreateSelfSigned` stalled before actual signing and also timed out. Both runs are evidence of **failure**, not actual signer acceptance. Final source replaces the private-key generation path with independently pinned Python OpenSSL PKCS#12, and uses **Microsoft SDK SignTool** for both real sign and verify. Confirm the new exact-head hosted Windows workflow succeeds before merging. The disposable credentials are not accepted as production CA certificates. If any run is queued/in progress/failed, retain PR and report the real blocker.

### Hosted operating-system compatibility isolation
The Authenticode test job is pinned to GitHub-hosted `windows-2022`, distinct from the ordinary cross-platform `windows-latest` source CI. This is a short-lived, standard **hosted** GitHub runner, never the owner's private Windows runner. The Windows-latest image repeatedly stalled on self-signed key operations; Windows Server 2022 plus OpenSSL-generated PFX and official SDK SignTool is independently tested before acceptance. A source-green run on a different Windows image does not waive native signing acceptance.

## Reconciled engineering plan after real hosted Windows crypto-store stalls (RUN7)

Native hosted Windows attempts from `New-SelfSignedCertificate`, .NET `CertificateRequest.CreateSelfSigned` and then OpenSSL-derived PFX with Windows CurrentUser certificate-store operations all failed to finish their bounded tests. The final prior hosted Windows-2022 [run #41598042290](https://github.com/rezamahrm100-ops/hamapp-store/actions/runs/41598042290) demonstrated `TWO_DISPOSABLE_OPENSSL_PFX_GENERATED_ONLY_IN_HOSTED_TEMP` before it timed out after 8 minutes **without** reaching the subsequent `AUTHENTICODE_TEST_SIGNING_COPIED_EXE_WITH_OFFICIAL_SDK` marker. The failure therefore occurred between PFX generation and the SDK signing marker, in a section also accessing the Windows certificate trust stores or locating SignTool. **No Windows-native signer trust/WinVerifyTrust success was established.**

Rather than weakening trust gates or repeatedly touching the blocked Windows certificate subsystem, the active CI pipeline now splits immutable binary building from real PE signature testing:

1. GitHub-hosted **Windows 2022** builds the **actual unsigned** PyInstaller native `.exe`, unit-tests it, and uploads an explicitly unsigned short-lived artifact.
2. Separate GitHub-hosted **Ubuntu 24.04** downloads that exact same-job artifact, installs Ubuntu's packaged real upstream `osslsigncode`, generates two independent disposable OpenSSL RSA code-signing certificate/PFX identities **inside `RUNNER_TEMP`**, and invokes actual PE/Authenticode embedded signature generation.
3. The test independently cryptographically verifies both real signed EXE copies using the respective exact certificate SHA-256 and CA trust, and **rejects unsigned original, different issuer and signer identity, and a modified signed PE byte**. It ensures original EXE checksum/size remain unchanged. Temporary PFX, password files and signed EXE copies are destroyed before only a bounded safe JSON receipt is uploaded.
4. This is genuine **portable Authenticode/PE cryptographic acceptance**; it is **not native Windows OS trust-store acceptance**, a production public CA or publisher identity, Windows SmartScreen reputation, a signed public installer, or install/upgrade on an owner machine. The separate original native Windows signing scripts are retained as diagnostic candidates but are **not invoked** by the accepted workflow. Never mark this work as production-ready on a green portable test.

The active workflow is `.github/workflows/windows-client-preview.yml` and the actual cryptographic engine is `scripts/portable_authenticode_drill.py`. The branch must pass its exact current SHA Windows build + actual Ubuntu cryptographic job + CI/CodeQL/Trivy before a source merge. Owner personal Windows runner remains main-only and never runs unreviewed PR source.
